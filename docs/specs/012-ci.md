# Spec 012: CI for the compiler repo

**Author:** Ritwik

## 1. Goal

Add a GitHub Actions workflow that builds the compiler and runs the full `ctest` suite on every push to `main` and every PR, across Linux and macOS. The compiler now has 20 test binaries guarding a frontend + interpreter that we spent this whole session hardening (specs 007–011 fixed a parser hang, two reference-invalidation bugs, wired diagnostics, and removed dead code). Nothing currently re-runs those tests on a clean machine — a regression could land unnoticed. CI is the bookend that protects the bug-fix sprint.

This mirrors the runtime's CI in intent, adjusted for two compiler-specific facts: (1) the compiler pulls `external/core-runtime` as a git submodule, so checkout must be recursive; (2) the compiler's CMake does **not** wire sanitizer build options (those are runtime-only), so the matrix is OS-only — no ASAN/UBSAN axis.

## 2. Invariants

- A workflow file exists at `.github/workflows/ci.yml`.
- It triggers on every `push` to `main` and every `pull_request` (any base).
- The job matrix is `{ubuntu-latest, macos-latest}` — 2 jobs.
- Each job: checkout **with submodules recursively initialised**, configure with CMake, build with `cmake --build`, run `ctest --output-on-failure`.
- A job fails (CI red) if any of: submodule checkout fails, CMake configure fails, the build fails, or any of the 20 ctest binaries fails.
- The submodule (`external/core-runtime`, pinned at v1.4.0) is fetched by the checkout; the build's `add_subdirectory(external/core-runtime)` then resolves, and `ZERO_BUILD_TESTS=OFF` (already forced in the compiler's top-level CMake, spec 001) keeps the runtime's own suite from running inside the compiler build.
- No dependency beyond the runner's default toolchain (CMake + system C++20 compiler). The project is C++20; `ubuntu-latest`'s default gcc and `macos-latest`'s AppleClang both support it.

## 3. API surface

New file: `.github/workflows/ci.yml`. Pure infrastructure — no source, no headers, no tests touched.

### Workflow shape

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-and-test:
    name: ${{ matrix.os }}
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, macos-latest]
    steps:
      - name: Checkout (with submodules)
        uses: actions/checkout@v4
        with:
          submodules: recursive

      - name: Configure
        run: cmake -B build

      - name: Build
        run: cmake --build build --parallel

      - name: Test
        run: ctest --test-dir build --output-on-failure --parallel
```

## 4. Acceptance tests

The workflow itself is the test. The acceptance signal is the first green run on `main` after this commit. Local pre-flight (proxy for the CI environment) before committing:

1. `git submodule status` shows `external/core-runtime` checked out (no leading `-`).
2. A clean local build (`rm -rf build && cmake -B build && cmake --build build`) succeeds.
3. `ctest --test-dir build` is 20/20 green.

(These are exactly what the workflow runs; CI re-runs them on Linux + macOS from a fresh checkout.)

## 5. Out of scope

- **Sanitizer matrix (ASAN/UBSAN/TSAN).** The compiler's CMake doesn't wire sanitizer options today (the runtime does, but those flags don't propagate to the compiler's own targets). Adding them is a separate CMake change; once wired, a sanitizer axis can be added to this matrix. Noted in `DEFERRED.md`.
- **Windows / MSVC.** The compiler hasn't been built on MSVC; adding it needs flag handling and is deferred until a concrete need.
- **Caching** (ccache, submodule cache, CMake cache). A perf optimisation, not needed for correctness at this scale.
- **Coverage reporting, static analysis (clang-tidy), lint.** Each is its own future item.
- **Release/packaging automation.** The compiler is pre-1.0; no release artifacts.
- **Matrix over compiler versions** (gcc-12 vs gcc-13, etc.). The default runner toolchain is sufficient.
- **Running the runtime's own test suite.** Explicitly kept off via the existing `ZERO_BUILD_TESTS=OFF`.
